From the master database's work list to the data mart

Workpaper Studio · walked through the screens on 2 November 2026 · synthetic people and data · the limit and method are fictional demonstrations

The master database says what to test. Studio opens each line as a case, already filled with what the database knows. People do the work, and every released case, every answer with its state, lands in a data mart where results can be read across cases.

The route

A red ring marks the control each step is about. Where the thing to read is small, a close-up is shown first and the full screen after it.

Set who can do what

1. Read or change the access levels

Admin (M. Okafor)

Do. Go to Access. Each column is one of this organization's levels; tick what it may do. Add a level or a person in the last column or row, then Save as a new version.

A correct screen. The levels and people as the organization set them, the extra rules (such as a second person for limits), and what is always true whatever is ticked: nobody reviews work they entered or approves a tool they proposed, and every action is logged.

Load the work

2. Load the work list from the master database

Admin

Do. On Cases, under Work from the master database, click Load the work list on the tool's row.

A correct screen. A green banner counts what happened: loaded, already here, refused. Open Why each was refused to read each refused line's reason, in words. Here one line names a facility type the tool's list does not have, and one names a preparer nobody has heard of. The master database is only read.

Do the work

3. Pick a case from Assigned to me

Preparer (A. Rivera)

Do. Sign in as the preparer. Assigned to me lists the lines the master database gave you, with the line number it uses.

A correct screen. Only your own cases. Filter by tool, status, or search by line, case, subject or person.

4. Open it: what the database knew is already filled in

Preparer

Do. Click the case.

A correct screen. Tester, reviewer, quarter, borrower, security and the facilities are already there, and the strip counts only what is left (12 here). Everything else is the same as a case started by hand.

5. Correct a value the master database got wrong

Preparer

Do. Type over it, like any entry.

A correct screen. The new value is kept and logged old → new. It stays marked as changed from the master database, all the way to the data mart (see step 8). Nothing is overwritten quietly.

Release

6. Finish, review, approve and release as before

Preparer, then reviewer

Do. Complete the questions and analysis, record the exception, submit. The reviewer acknowledges it, approves and releases (the first procedure covers each step).

A correct screen. Outputs now lists four released files: the data feed (JSON and CSV), the workbook, and answers-row.csv, every answer of the case in one row, the shape a master table loads.

See the results

7. Read the results across cases

Anyone with access

Do. Click Results.

A correct screen. From the data mart, across released cases: how each question was answered; every partially or not effective answer with its comment (the root-cause list); results against limits; exceptions by reason; every answer that differs from what the master database sent. Take the data downloads each table as CSV.

8. Trace where each value came from

Anyone

Do. Open the case's History.

A correct screen. The oldest entries, at the foot of the list, are loaded: one per value, each naming the master database and the line. Every change after that is someone's, with old and new.
