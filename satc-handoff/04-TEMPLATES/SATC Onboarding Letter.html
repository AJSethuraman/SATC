Merge fields

Sent with the engagement letter and the fee estimate, as the third document in the opening package — it is the one a client actually acts on, so it carries the deadline and the checklist and nothing legal. Same conventions: <<Field>> substitutes, [[IF Flag]] … [[END IF]] keeps or drops, [[EACH List]] … [[END EACH]] repeats. Fail the render on any unresolved << or [[.

FieldRequiredExample / notes
<<LetterDate>>RequiredFebruary 3, 2027 — the package's date. Same value across all three documents.
<<EngagementRef>>Required2027-0114 — the join key, byte-identical to the letter's and the estimate's
<<PeriodLabel>>RequiredSelf-describing. "2026 tax year" or "Monthly, from July 2027" — the same field the fee estimate uses, so the package reads as one thing. Appears twice.
<<ClientFullName>>RequiredMr. and Mrs. Daniel Reyes — the addressee block AND the salutation, so both read the same
<<ClientAddress1>> <<ClientCity>> <<ClientState>> <<ClientZip>>RequiredSame four fields as the letter, from the same record
<<ClientEmail>>Requireddreyes@example.com — printed on purpose. Both the upload link and the Encyro signing invitation go to this address, and it is the first thing a client asks.
<<MaterialsDeadline>>RequiredMarch 15, 2027 — a real date, never "early March". Set in one place; the tax letter's section 04 carries the same value.
[[EACH RequestList]]ListOne or more. Two sub-fields per item. This is the whole point of the letter — build it from the engagement type, not by hand.
<<Item.Document>>RequiredAll W-2 forms — as a client would name it, not as the tax code does

18 fields + 1 repeating list of 2 + 1 flag.

Section numbering under a dropped block

This is the first template where a conditional removes a numbered section. Two options, and the software must pick one: renumber sequentially after the merge (preferred — a client should never see 03 followed by 05), or make the numbers static and accept the gap. Do not leave it to chance; the numbers exist so a client can point at a clause on the phone.

Deliberately not here

  1. No fee, no scope, no terms. The letter and the estimate own those. This document is a to-do list with a date on it.
  2. No signature line. Three signature blocks in one package guarantees one comes back blank.
  3. No "please don't hesitate to contact us". Section 06 asks for the question outright, which is the behaviour you actually want.

For whoever wires the software

  1. The checkboxes are printed squares, for a client working on paper. Do not turn them into form fields — a half-completed PDF form is worse than a list.
  2. The [[EACH RequestList]] markers sit outside <ul class="req-list">: repeat the whole ul per item, or move the markers inside and repeat the li. Either works; be consistent with how the fee estimate's row repeat is wired.
  3. Strip the .f class and the .cond markers on the client-facing render.
  4. Name the output: SAT-C What We Need — Reyes — 2026.pdf. Plain language beats "onboarding" on a client's desktop.
